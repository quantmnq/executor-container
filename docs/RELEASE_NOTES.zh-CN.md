# Auto Quant 0.4.3 — 各 Gateway 版本均可读取账户净值

[English](RELEASE_NOTES.md) | 简体中文

准备日期：2026 年 11 月 13 日（美国太平洋时间）。基于 0.4.2。
交易规则、仓位区间和计算公式、杠杆比例、保护规则、风险限制、依赖和 Gateway 镜像均不变。

## 0.4.3 新增内容

- **在各个 Gateway 版本上，余额仓位都能持续读取账户净值。** IBKR 每个连接最多保留两个未结束的账户净值
  （账户汇总）请求，而 Gateway 会忽略用于结束请求的新 protobuf 格式消息。0.3.2 只在连接协商 API 版本 226
  （随附的 Gateway 即是如此）时发送 Gateway 会执行的旧格式消息。对于协商更早版本（207 至 225）的 Gateway，
  每次读取都不会结束，同一连接上第二次之后的每次读取都以 IBKR 错误 322 失败，之后入场会沿用上一次的仓位基数，
  如没有基数则拒绝入场。执行器现在无论协商哪个版本，都以旧格式结束每次账户净值读取；其他 API 消息仍使用客户端的常规格式。
- **读取失败时仍说明原因并结束请求。** 被 IBKR 拒绝或超时的读取同样会被结束，拒绝原因连同 IBKR 错误代码
  （例如 `account summary refused (322)`）写入日志。
- **固定数量配置不变**，不读取账户净值。
- **可从 0.4.2 直接升级。** 交易日志、配置和 Gateway 代码与 0.4.2 完全相同。0.3.0 至 0.4.1 通过 0.4.2
  经过审查的迁移升级，同时获得 `risk.max_margin_fraction` 默认值 1.0；0.2.0 和 0.1.12 保留经过审查的升级路径。

## 更新到 0.4.3

从 0.4.2、0.4.1、0.4.0、0.3.2、0.3.1、0.3.0、0.2.0 或 0.1.12 升级，请按 [UPGRADE.zh-CN.md](UPGRADE.zh-CN.md) 操作：
在账户没有阻止维护的持仓或活动订单时从旧目录停止执行器，保持 Gateway 登录，将 0.4.3 解压到新目录，运行
`./follow-stack upgrade --from <旧目录>`。两个服务均保持停止。从 0.3.0 或更新版本升级时无需选择
杠杆比例，仓位设置会保留。

## 保留的 0.4.1 功能 — K 线中段读取账户净值

- **读取账户净值不再耽搁执行器。** 使用余额仓位时，此前的版本在空仓期间每 30 秒读取一次 IBKR
  NetLiquidation，且在交易循环中进行；IBKR 响应缓慢时，信号和订单要等读取返回后才能处理。
  0.4.1 每根 5 分钟 K 线读取一次，时间为该 K 线开始后第 2:00 至 3:00 分钟（美东时间），读取与交易循环
  并行：信号、止损调整以及成交后的止损下单都不会等待它。
- **仅在空仓时、仅在常规交易时段内读取。** 读取只在纳斯达克常规交易时段进行（美东 09:30–16:00，
  提前收盘日为 13:00，周末和交易所假日不读取），且仅当最近一次券商对账显示没有持仓和活动订单时进行。
- **读数有效时入场直接使用。** 如果读数不超过 360 秒，且读取之后没有记录任何成交，入场就使用该读数；
  否则仍按原方式直接读取 NetLiquidation。重启或 IBKR 重新连接会丢弃该读数。
- **记录在交易日志中。** 每次读取记录为 `balance_reading`，每次失败记录为 `balance_reading_failed`，
  失败不会发送告警。每次入场的 `balance_size` 记录包含 `net_liquidation_source`（`mid_bar_reading` 或
  `direct_read`），以及读数的时长或未使用的原因。`./follow-stack status` 中的
  `sizing.account_value_health` 现在在这些读取和入场时更新，见[账户净值读取](OPERATIONS.zh-CN.md#余额仓位的账户净值读取)。
- **固定数量配置不变**，也不读取账户净值。

## 保留的 0.4.0 功能 — 执行器性能保持稳定

- **执行器不再随成交增多而变慢。** IBKR 连接会保留执行器启动以来的所有成交，而执行器每一步都会把它们
  重新记录一遍，每次都要搜索交易日志中的成交记录。每一步的耗时随历史成交数的平方增长：500 笔成交后约
  40 ms，2,000 笔后约 450 ms，同时拖慢下单和移动止损。执行器现在每个进程只记录每笔成交一次，并且只在
  有新成交或 resume 之后才重新计算交易日志的预期持仓；2,000 笔成交时每一步不到 1 ms。
  交易日志的格式和内容不变。
- **行情报价不再触发额外的步骤。** 实时报价只用于健康状态报告，但此前每个报价都会运行一次完整的执行器步骤。
  现在报价按常规的 0.25 秒周期读取；行情订阅出错时仍会立即唤醒执行器。
- **先停执行器，再停 Gateway。** 执行器服务运行时，`./follow-stack gateway stop` 现在会拒绝执行，
  与容器指南原有的要求一致：运行中的执行器需要 Gateway 来管理退出。Gateway 服务自身的重启不受影响。
- **不会再把持仓显示成空仓。** 对于交易日志从未记录过品种的持仓合约（例如使用余额仓位时由 `resume`
  接管的手动持仓），`./follow-stack status` 和执行器日志会显示为 `UNKNOWN`。此前它会被略去，
  组合可能显示为 `flat`。
- **从 0.3.0、0.3.1 或 0.3.2 升级。** 交易日志、配置和 Gateway 代码完全相同，无需迁移，余额仓位会保留
  （回滚时也一样）。0.2.0 和 0.1.12 保留经过审查的升级路径。

## 保留的 0.3.0 功能 — NQ + MNQ 余额仓位

准备日期：2026 年 10 月 28 日（美国太平洋时间）。在领单方当前的仓位方式下，每笔交易按领单方余额
和信号携带的权重计算仓位。0.3.0 让跟单端按领单方杠杆的一定比例同样计算，
将 NQ 加 MNQ 余数作为一个组合交易。依赖、Gateway 镜像及保护规则保持不变。


- **杠杆比例。** 安装向导询问 `f`，大于 0 且不超过 1；`1` 表示按领单方 6 倍余额仓位及
  5.88–6.6 倍区间跟随。配置为 `"sizing": {"mode": "balance", "leverage_fraction": f}`。
  向导会预览示例权重下的 NQ/MNQ 数量；`check` 按 IBKR NetLiquidation 和实时 NQ 报价显示，
  并给出权重为 1（最大仓位）时的组合保证金。
- **每次空仓新入场时计算。** 基准为 `floor(6f·E / (2·P))` 个 MNQ 单位（`E` 为
  NetLiquidation，`P` 为参考价），之后在信号区间乘以 `f` 后的范围内保持、重置或逐个单位增加。
  每个信号都带有该笔交易的 `sizing.weight`（大于 0 且不超过 1），跟单端使用收到的权重：
  该笔交易为 `round_half_up(基准 × weight)` 个单位，即 NQ 加 MNQ 余数，例如 `1 NQ + 7 MNQ`。
  没有最低数量：取整为 0 的交易不发送订单并标记拒绝（`size rounds to 0 contracts`）；
  基准为 1 时，权重 0.4 取整为 0。缺少余额或价格时沿用上次的基准；没有历史基准、基准为 0、信号缺少
  `sizing` 或单笔订单超过 `risk.max_quantity` 时拒绝入场并说明原因。已有持仓不会重新
  计算数量，Gap→Drift 延续也不例外。
- **一个双合约组合。** 发送任一订单前，对整个组合检查保证金和止损风险。每种合约都有
  自己的止损（价格与领单方相同），并执行移动止损、开盘前计划撤单和平仓、收盘平仓、
  紧急平仓及重启核对。如果只有一种合约的止损成交，另一种保留止损并按计划退出。
  只允许同一月份的一张 NQ 持仓和一张 MNQ 持仓，其他组合会触发暂停。
- **信号。** 文档新增 `target.sizing`（该笔交易的权重和杠杆区间）以及 Drift 退出计划的
  `minutes_before_open`。同时接受 `next_rth_open` 和 `before_next_rth_open`，
  包括经过核实的开盘前撤单例外。
- **通知与状态。** Discord 为每种合约分别发送持仓消息，各自显示品种和盈亏；`status`
  显示组合，例如 `1 NQ + 5 MNQ`。启动确认包含仓位，例如 `START PAPER BALANCE 0.5`。
- **升级。** 新增中英文[升级指南](UPGRADE.zh-CN.md)。`follow-stack upgrade` 接受经过审查的
  0.2.0 → 0.3.0 迁移（交易日志和 Gateway 代码不变，0.2.0 设置可原样读取）。回滚前须改回固定数量。
- 不含 `sizing` 的配置（包括所有 0.2.0 配置）保持 0.2.0 的行为：单一品种、相同且不加权的数量。

## 从 0.2.0 更新

在整个账户空仓时：从 0.2.0 目录停止执行器，保持 Gateway 登录，交易日志和令牌保持原位。
将 0.3.1 安装包解压到新目录，运行 `./follow-stack upgrade --from <0.2.0 目录>`；它会重新生成
两个服务并保持停止。然后依次运行 `./follow-stack gateway start`、用 `./follow-stack settings`
选择杠杆比例、`./follow-stack check`，最后明确执行 `./follow-stack start`。详见
[UPGRADE.zh-CN.md](UPGRADE.zh-CN.md)。

## 如果继续使用 0.2.0

0.2.0 会继续按固定数量交易。它忽略新的 `sizing` 字段；领单方发送 `next_rth_open` 退出
计划（开盘前撤销止损并平仓），因此其开盘前计划撤单保护仍然有效。它不会使用信号权重或账户余额。

## 保留的 0.1.12 功能

- 观察到入场成交（包括部分成交）后，执行器等待最多 **30 秒**，确认券商已接受
  与当前持仓合约、方向及数量相匹配的止损单。保护仍缺失时，在订单／持仓对账后
  启动紧急平仓。
- 已有止损意外被撤销、丢失或不再匹配持仓时，允许 **60 秒**恢复保护，否则启动紧急平仓。
- 经验证由策略主动发起、位于计划开盘平仓前一分钟内的撤止损，使用原计划平仓时间
  加最多 **30 秒**平仓宽限，不会再额外等待 60 秒。意外撤单及入场后未成功建立止损
  不适用此例外。
- 最新完整券商快照确认持仓为空但执行器自己的止损仍有效时，会撤销遗留止损，
  并在完成对账前阻止新开仓。即使执行器处于保护性暂停状态，此清理仍会运行。
  清理期间若自己的订单成交，会平掉经核实产生的持仓；不会接管其他账户或客户端订单。
- 保护期限及清理状态在执行器重启后保留。紧急平仓会先核实已有平仓单和成交，
  避免重复提交平仓单。
- 示例 JSON 按要求使用 `max_margin_fraction: 1.0`，不修改向导默认值或客户已有配置。

这些保护需要执行器运行且券商连接正常。断线、回报延迟或市场关闭可能延迟实际平仓；
30／60 秒是保护期限，不是成交时间保证。参阅[交易执行与安全机制](EXECUTOR.zh-CN.md)。
