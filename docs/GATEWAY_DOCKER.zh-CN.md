# Gateway 容器试用方案

[English](GATEWAY_DOCKER.md) | 简体中文

这个可选方案使用 [gnzsnz/ib-gateway-docker](https://github.com/gnzsnz/ib-gateway-docker)
提供的镜像，替代手动安装 Gateway 和完整 Ubuntu 桌面。Auto Quant 执行器仍通过原有字节码安装包和服务运行。
请使用 **Ubuntu 24.04 ARM64 和 IBKR 模拟账户**测试。已有的兼容测试机器即可用于账户检查，
不强制使用 OCI。修改 Gateway 设置前，应停止交易并确认没有持仓或挂单。
推广前用干净虚拟机验证首次安装和重启很有帮助，但不是必须现在新建一台虚拟机。
已完成的试点结果及当前准备状态见[版本说明](RELEASE_NOTES.zh-CN.md)。既有安装保留原后端，
迁移需明确安排。容器不会代替云电脑创建或 IBKR 手机认证。

## 安装与配置

完成[安装指南](SETUP.zh-CN.md)第 1–4 步，包括校验安装包及运行 `./install.sh`。
将第 5 步替换为以下流程；不用运行 `gateway-desktop.sh`，也不用手动安装 Gateway。

1. 在 Ubuntu 的安装目录运行：

   ```bash
   ./scripts/install-docker.sh
   ```

   脚本使用 Docker 官方 Ubuntu 软件源安装引擎、启用服务，并将当前 Ubuntu 用户加入 Docker 组。
   该组成员可以管理整台虚拟机，请使用客户专用机器。脚本不会自动删除冲突的容器软件包。
   支持本机 Docker Engine 28 或更新版本，使用普通 rootful 模式，不支持用户命名空间重映射。

2. 首次安装后，用 `sudo reboot` 重启虚拟机一次。重新 SSH 登录并返回安装目录。
   重启使终端和用户服务管理器都获得新的组权限；只开一个新终端可能仍不足以更新服务权限。

3. 配置 Gateway：

   ```bash
   ./follow gateway configure --backend docker --vnc
   ```

   向导下载固定摘要的 ARM64 镜像，再询问账户模式、时间安排及凭据。
   新配置默认为 **paper**、`America/New_York`、每日 `23:45`、周日 `12:00`。
   继续已有配置时保留已保存的时间。IBKR 用户名及密码只在自己的终端输入，不要放入聊天或支持消息。

   `--vnc` 开启用于首次登录检查的私密恢复画面。设置恰好 **8 个可打印 ASCII 字符**的独立密码，
   不要使用 IBKR 密码。VNC 密码长度受协议限制，连接隐私由 SSH 隧道保护。
   新配置不加 `--vnc` 时默认关闭画面；再次配置会保留已选后端和画面开关。

4. 启动 Gateway；如出现预期的手机登录请求，完成批准：

   ```bash
   ./follow gateway start
   ./follow gateway status
   ```

   在自己的电脑建立恢复画面的隧道，将密钥位置和地址替换为自己的值：

   ```bash
   ssh -i ./auto-quant.key -N -L 5901:127.0.0.1:5901 ubuntu@YOUR_OCI_PUBLIC_IP
   ```

   保持该窗口打开。TigerVNC 使用 **localhost::5901**，分开输入的查看器使用主机 `localhost`、端口 `5901`。
   画面中只有 Gateway，没有完整 Ubuntu 桌面。自行处理 IBKR 提示和适用条款，按照
   [API 设置截图](SETUP.zh-CN.md#gateway-api)检查首次登录。
   Gateway 内部端口为 **模拟 4002 / 实盘 4001**；自定义主机端口由 Docker 转换，不要把内部端口改为主机端口。

5. 返回[第 6 步](SETUP.zh-CN.md#follower)，填写中继、账户和数量，可选关联 Discord，运行 `./follow check`。
   检查通过并决定开始模拟交易后，才运行 `./follow start`。安装或启动 Gateway 不会启动交易执行器。

使用第三方镜像前，请审阅适用于自己的 IBKR 账户和软件的条款。
镜像直接从上游拉取；Auto Quant 安装包不包含 IBKR 二进制文件。

## 日常操作与恢复

两种后端都使用原有的 `gateway start`、`stop`、`status`、`logs` 命令。
`start` 启用开机启动，由用户服务管理容器重启；Docker 自己的容器重启策略关闭。
停止 Gateway 会禁用自启并停止容器，保留数据。执行器服务运行时拒绝停止 Gateway。
停止命令不会平仓或撤销券商订单。

`gateway status` 显示镜像、进程状态、恢复画面开关和数据卷名称。
**容器正在运行不代表账户已经登录。** 执行器停止时，用 `./follow check` 验证账户访问、
持仓/订单、中继签名和可取得的模拟保证金结果。

| 问题 | 下一步 |
| --- | --- |
| Docker 不可用或权限不足 | 检查 Docker 已安装并运行；首次修改用户组后重启虚拟机一次 |
| 等待登录 | 批准预期的 IBKR Mobile 请求；用 VNC 查看剩余弹窗 |
| 两次尝试后显示需要处理登录 | 准备好后运行 `./follow-stack gateway start`（独立安装包用 `./follow gateway start`），批准新请求，再检查就绪 |
| 常规用户名关联多个模拟交易用户 | 停止且空仓时，配置目标模拟交易用户名及对应密码，保留 paper 模式 |
| 已有其他 IBKR 会话 | 主动关闭旧会话；保留原有 `secondary` 行为，不自动抢占 |
| 5901 端口被占用 | 空仓并停止服务后关闭原生桌面服务，再使用容器画面 |
| 镜像摘要与当前版本不符 | 按下面的升级步骤重新配置，不要手工改摘要 |
| 进程运行但检查失败 | 查看检查结果和私密 Gateway 日志，不能以进程状态代替认证结果 |

以后开启或关闭恢复画面时，先确认空仓且没有挂单，停止执行器和 Gateway，再运行
`./follow gateway configure --backend docker --vnc` 或 `--no-vnc`。向导会再次询问凭据。
随后启动 Gateway、批准所需登录、检查账户，再主动重启执行器。
每周手机认证以及 IBKR 额外要求的认证仍然需要完成，详见 [IBC 时间安排](IBC.zh-CN.md)。

Docker 启动器给手机批准五分钟时间。若仍未完成登录，会停止该 Gateway，由服务在
60 秒后进行一次全新登录。Gateway 随后可能在 `Authenticating...` 等待一段时间才显示
下一个批准窗口；窗口出现不代表手机已收到通知。划掉旧通知，收到新通知后及时批准。
第二次超时后停止 Gateway，`gateway status`
显示 `login_recovery.attention_required=true`，不继续发送请求。准备好批准后，显式运行
`gateway start` 只会在 Gateway 已停止时重置次数；服务重启或主机重启不会重置次数。
成功登录会清除限制；此计时器不会重启已经认证的 JVM。之后每周新 JVM 重启可以
开始新的批准窗口。

如果手机没有收到通知，按 [IBKR 通知排障说明](https://www.ibkrguides.com/kb/en-us/article-3234.htm)
检查，其中包括私下用手动挑战／响应方式登录一次 Client Portal 来重新同步通知。
重试 Gateway 前退出 Client Portal；不要在聊天或支持日志中分享挑战码或响应码。

重试由主机控制程序负责，容器私密配置副本会禁用 IBC 自身重叠的超时重登录循环，
也兼容旧版已保存配置。Gateway 服务日志只显示筛选后的登录／恢复事件，不直接输出
原始 IBC 日志。私密 `gateway/login-recovery.json` 保存重试限制，不要删除或编辑以绕过
需要处理的状态。这些变化适用于新构建安装包；旧安装在明确升级前保持原有行为。

同一监督进程现会在成功登录一分钟后开始每分钟检查 API，使用保留客户端 ID **9701**，
等待 API 握手及受管账户响应，并私下核对已配置账户。探针不请求行情、不读取交易日志、
不下单、不撤单。组合安装包通过该版本固定的执行器镜像运行探针，只以只读方式挂载
执行器配置文件，不启动交易进程。执行器及其他 API 客户端不要使用 ID 9701。

连续十次 API 不可用会请求重启 Gateway；30 分钟重启冷却期持久保存，服务或主机重启
不会清除。登录、每日及每周 JVM 重启期间暂停监控，丢弃旧探针结果，由原有限次手机
批准恢复机制负责。停止 Gateway 也会停止监控，没有另一个定时器把它重新启动。
探针／镜像错误、客户端 ID 冲突或账户不匹配只会在服务日志和 `api_health` 状态中提示
处理，不触发 Gateway 重启。券商行情服务器消息本身不算本地 API 握手失败。

`gateway status` 中 `api_health` 是带检查时间的**缓存**结果，旧的健康结果不代表当前
已就绪。监控不验证行情权限／新鲜度、中继、保证金或订单核对；主动开始交易前仍须
执行完整就绪检查。

手动恢复登录：

1. 查看 `./follow-stack gateway status` 和 `./follow-stack gateway logs`。
   如果已提示登录需要处理且 Gateway 已停止，准备好批准后运行 `./follow-stack gateway start`。
2. 如果 Gateway 仍运行但登录卡住，先在 IBKR 确认账户空仓且没有挂单，再依次运行
   `./follow-stack stop`、`./follow-stack gateway stop`、`./follow-stack gateway start`。
   这些命令不会平仓或撤单。如果 API 不可用且还有敞口，先通过 IBKR 管理敞口再进行计划维护。
3. 划掉旧通知，不批准旧请求；只及时批准预期的新请求，不要反复点击 Resend。
   没有新通知时，按上面的 IBKR 排障链接和私密恢复桌面说明操作。
4. 执行器停止时运行 `./follow-stack check`。通过后，只有打算交易才显式运行
   `./follow-stack start`。独立安装包将上述 `./follow-stack` 替换为 `./follow`。

10 月 18 日的真实模式验收已验证一次自动重试后新通知的送达和批准，以及认证后的
API 恢复。监控本身不能保证未来每次推送都能送达，仍需保留手动恢复方法。

## 私密数据、升级及切回原生安装

主机 `gateway/ibc.ini` 继续以 `0600` 权限保存凭据。
一个短暂运行、禁用网络的初始化容器将其复制到私密 Docker 数据卷，供镜像的 UID 1000 用户读取。
这样即使 Ubuntu 用户 UID 不同，也不用放宽主机密码文件权限。
正式 Gateway 进程使用 UID 1000，移除 Linux capabilities 并禁止提权。
IBKR 密码不出现在 Docker 环境变量或命令行参数中。

Docker 卷保存另一份 IBC 凭据、可选 VNC 密码以及持久 Gateway 设置，属于敏感数据。
卷名由 `gateway status` 显示。不要把卷内容发给支持人员，也不要用卷清理命令将其删除。
执行器配置和 SQLite 交易日志保留原位置；不要为了修复容器而重置交易日志。
API 与 VNC 只发布到 `127.0.0.1`，无需新增 OCI 入站端口。

每个 Auto Quant 版本固定不可变的镜像摘要；启动 Gateway 不会自动拉取新镜像。
Docker 引擎更新和 Gateway 更新是独立维护操作，均应在空仓且两个服务已停止时执行。
保留旧 Auto Quant 安装目录和镜像用于回退，并通过私密虚拟机备份流程保存主机配置、
交易日志以及停止状态下的 Gateway 卷。

如果新版本有意更换镜像摘要，停止两个服务，用新版本重新配置 Gateway 以选择新镜像。
旧摘要会被明确拒绝，不会静默替换。如果安装器的 `gateway refresh` 报摘要不符，
先用新版本运行 `gateway configure --backend docker`，然后重新运行安装器再启动。
回退时用保留的旧安装目录重新配置其镜像并检查账户。不要恢复过期的交易日志；
Gateway 设置只从兼容的停止状态备份恢复。

切回原生 Gateway 时，空仓后停止两个服务，按[原生安装指南](SETUP.zh-CN.md#gateway)准备好环境，
然后运行 `./follow gateway configure --backend native`。
从原生切到带 VNC 的容器时，还需停止并禁用旧桌面：
`systemctl --user disable --now follow-gateway-desktop.service`。
两种后端使用独立 Gateway 设置，不会导入彼此的登录会话。
保留同一份执行器配置和交易日志，确认账户后再启动；不要同时运行两个后端登录同一账户。

设为客户默认方案之前，在支持的 ARM64 环境记录以下测试结果，包括干净环境安装和重启验证：

- 首次登录、首次弹窗、API 设置及账户检查。
- 错过手机批准后的重试，以及已有会话处理。
- 已认证会话的每日重启、周日完整重启及所选时区行为。

- 升级和回退，保留 Gateway 设置及原执行器日志。
- 客户私密输入交接和向导中断后的继续操作。

使用 Docker 29.9.1。已验证预期模拟账户、完整持仓及订单快照、买卖双向 what-if 保证金检查和实时 MNQ 行情。

无论使用原生安装还是容器，这都是客户接入时需要检查的一项：退出占用行情的真实交易会话后重新检查实时行情，
仅 API 连接成功不能证明行情就绪。

Gateway 管理服务自动重建容器并恢复模拟账户认证、完整空仓快照、持久设置和实时行情。
共享 relay 服务进程及原执行器日志保持不变。这验证的是依赖本次权限修复的恢复过程，
并不证明客户重启后的干净环境能在无需干预时自动恢复。
